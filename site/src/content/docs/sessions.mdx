<Callout label="status">
**Sessions run today**, in a git worktree per session. Two parts are unbuilt:
starting sessions in a line's container (see [lines](/docs/lines)), and
jobs (see [the gaffer](/docs/gaffer)).
</Callout>

A session is one task in its own checkout that ends in a pull request. It's the
harness run headless (`claude -p`, `codex exec`) inside tmux on its host, one
turn at a time. The first turn is the task. Each `send` becomes the next turn,
resumed from the harness's own session, so a session that finished yesterday
picks up where it stopped.

## The tools

Your laptop's Claude gets a small command-line surface:

```bash
factory hosts                          # each host: identity, live sessions, load, memory, weekly plan use
factory run [--on HOST] REPO "TASK"    # a new session in its own checkout, prints its id
            [--harness claude|codex]
factory ls                             # every session on every host: running, done, failed, died; its PR
factory peek ID                        # the recent transcript
factory send ID "MESSAGE"              # a follow-up, taken as the session's next turn
factory wait ID...                     # block until none of them is running
factory attach ID                      # take over in tmux, then detach and leave it running
factory kill ID [--rm]
factory find "QUERY"                   # search every session's trace, on every host
```

Without `--on`, `run` places the session itself. It tries the always-on host
first, then spills to other hosts by free cores, free memory and subscription
headroom. It refuses rather than oversubscribe a machine.

## Fan out

Most real work breaks into independent parts: one change per repo, a migration
across twenty call sites, three approaches to compare. The coordinator runs
each part as its own session and reads the results:

1. Split the work into parts that can each end in their own pull request.
2. `factory hosts` to see where there's room, then one `factory run` per part.
3. `factory ls` and `factory peek` while they run, `send` to steer one, and
   `attach` to steer it yourself.
4. Review each pull request. `factory find` shows why a session did what it did.

None of the sessions waits on another. If one part depends on another, the
coordinator runs it after the first has landed.

## Jobs

A session ends at its pull request. Work that needs several sessions in order,
or needs to keep going after you close the laptop, is a **job**. Its
[gaffer](/docs/gaffer) runs the sessions for you. A job with a done-when check
and one part is what an earlier draft of this page called a goal.
