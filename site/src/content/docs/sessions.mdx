A session is one task in its own checkout that ends in a pull request. It's the
harness run headless (`claude -p`, `codex exec`) inside tmux on the factory's
Mac, one turn at a time. The first turn is the task. Each `send` becomes the next turn,
resumed from the harness's own session, so a session that finished yesterday
picks up where it stopped.

## The tools

[Reception](/docs/reception) and [gaffers](/docs/gaffer) start and steer
sessions with a small command-line surface:

```bash
factory host                           # identity, live sessions, load, memory, weekly plan use
factory run REPO "TASK"                # a new session in its own checkout, prints its id
            [--harness claude|codex]
factory ls                             # every session: running, done, failed, died; its PR
factory peek ID                        # the recent transcript
factory send ID "MESSAGE"              # a follow-up, taken as the session's next turn
factory wait ID...                     # block until none of them is running
factory attach ID                      # take over in tmux, then detach and leave it running
factory kill ID [--rm]
factory find "QUERY"                   # search every session's trace
```

`run` refuses rather than oversubscribe the Mac. It checks free cores, free
memory and subscription headroom first.

<Edition only="pro">

## From your laptop

In pro, sessions run on the always-on host and your laptop is a client of it.
Every `factory` command you or reception run on the laptop runs on the
server, so `run`, `ls`, `peek` and `attach` all act on the server's sessions,
committed as the [bot account](/docs/identity). Work you want under your own
name you do yourself, not through the factory.

</Edition>

## Fan out

Most real work breaks into independent parts: one change per repo, a migration
across twenty call sites, three approaches to compare. Reception runs
each part as its own session and reads the results:

1. Split the work into parts that can each end in their own pull request.
2. `factory host` to see how much room there is, then one `factory run` per part.
3. `factory ls` and `factory peek` while they run, `send` to steer one, and
   `attach` to steer it yourself.
4. Review each pull request. `factory find` searches the [traces](/docs/traces) for why a session did what it did.

None of the sessions waits on another. If one part depends on another, it
runs after the first has landed.

## Jobs

A session ends at its pull request. Work that needs several sessions in order,
or needs to keep going when nobody is watching, is a **job**. Its
[gaffer](/docs/gaffer) runs the sessions.
